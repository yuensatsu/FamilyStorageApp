# AI駆動開発をゲーム制作に取り入れる型

Spring Boot講習の核心である「理解は人、生成はAI」を、ゲーム制作では
「遊びの判断は人、実装の下書きはAI」として扱います。

## 1. まず置き換える考え方

| Spring Webアプリ | ゲーム制作での対応 |
| --- | --- |
| Controller | 入力受付、画面遷移、UIイベント |
| Service | ゲームルール、勝敗判定、スコア計算 |
| Repository | セーブデータ、設定、マスターデータの読み書き |
| Entity | プレイヤー、敵、アイテム、ステージなどのデータ |
| Form | メニュー入力、名前入力、設定画面 |
| templates/static | UI画面、画像、音、ステージデータ |

重要なのは、AIに「ゲームを作って」と丸投げしないことです。人間が遊びの核を決め、AIには小さな単位で実装させます。

## 2. 30分スプリントの流れ

### 1. 要件定義・設計: 5分

1回のスプリントでは、ゲーム全体ではなく「1つの遊びのループ」だけを対象にします。

例:

- プレイヤーが左右に動ける
- 敵が上から落ちてくる
- 敵に当たるとゲームオーバー
- 30秒生き残るとクリア

決める項目:

- プレイヤーが何をするか
- 何が成功か
- 何が失敗か
- 画面に何を表示するか
- 入力方法
- 必要なデータ

### 2. AIによるコード生成・論理検証: 15分

AIには、次の順番で依頼します。

1. ファイル構成を提案させる
2. 主要クラス、シーン、コンポーネントの責務を整理させる
3. 最小実装を生成させる
4. 正常系と異常系を説明させる
5. 動作確認手順を出させる

AIに最初から大量の演出、複雑なステージ、課金、オンライン要素を頼むと失敗しやすくなります。

### 3. 動作検証・微調整: 10分

人間が確認する観点:

- 操作して楽しいか
- ルールがすぐ理解できるか
- 失敗理由が納得できるか
- 難しすぎないか、簡単すぎないか
- バグが起きた時に再現手順を説明できるか

AIには「面白いかどうか」の最終判断を任せません。AIは候補を作る道具として使います。

## 3. 人間が最低限理解する構造

使用エンジンに関係なく、次の分担を理解しておくとAIへの指示が安定します。

- 入力: キーボード、マウス、タッチ、ゲームパッド
- 状態: タイトル、プレイ中、ポーズ、ゲームオーバー、クリア
- ルール: スコア、HP、制限時間、勝敗条件
- 表示: キャラクター、UI、エフェクト、カメラ
- データ: セーブ、設定、ステージ、アイテム表
- 音: BGM、効果音、音量設定

## 4. AIに任せやすい部分

- 既存仕様に沿ったコードの下書き
- 当たり判定やタイマーなどの定番処理
- UI表示の仮実装
- テスト観点の洗い出し
- リファクタリング案の作成
- エラー原因の候補出し
- READMEや仕様書の整備

## 5. 人が判断すべき部分

- どんな体験を作りたいか
- 操作感が気持ちよいか
- 難易度が適切か
- キャラクターや世界観が魅力的か
- どの機能を削るか
- どの不具合を優先して直すか
- 完成とみなす基準

## 6. そのまま使えるプロンプト

### 新しい機能を作る時

```text
あなたはゲーム開発の実装補助AIです。
次の仕様を、最小構成で動く形にしてください。

使用環境:
- エンジン:
- 言語:
- 対象シーン:

作りたい機能:
- （ここに記入）

プレイヤーの操作:
- （ここに記入）

成功条件:
- （ここに記入）

失敗条件:
- （ここに記入）

画面に表示するもの:
- （ここに記入）

制約:
- まず最小実装にしてください
- 既存ファイル構成を崩さないでください
- 変更するファイルと理由を先に説明してください
- 実装後に動作確認手順を出してください
```

### バグ修正を依頼する時

```text
次のバグを調査してください。

現象:
- （ここに記入）

期待する動作:
- （ここに記入）

実際の動作:
- （ここに記入）

再現手順:
1.
2.
3.

関係しそうなファイル:
- （ここに記入）

依頼:
- 原因候補を重要度順に出してください
- 修正方針を説明してください
- 最小限の修正だけを提案してください
- 修正後の確認手順も出してください
```

### 企画を小さく分割する時

```text
次のゲーム企画を、AIで実装しやすい小さな機能単位に分割してください。

企画:
- （ここに記入）

必ず含めたい体験:
- （ここに記入）

今回作る対象:
- 1人用
- オフライン
- まずはプロトタイプ

出力してほしい内容:
- 最初の30分で作る最小機能
- 次に追加する機能
- 後回しにする機能
- 人間が判断すべき面白さの確認ポイント
```

## 7. 最初に作る題材の例

初回は複雑なゲームではなく、次のような題材が向いています。

- クリックでスコアが増えるゲーム
- 敵を避けるミニゲーム
- 迷路をゴールまで進むゲーム
- カードをめくって一致させるゲーム
- 簡単なターン制バトル

どれも「入力」「状態」「ルール」「表示」が明確なので、AIに指示しやすいです。

## 8. 導入時の注意点

- 最初から大作を目指さない
- 1回の依頼で複数ジャンルを混ぜない
- AIの出力を読まずに貼り付けない
- 動いたらすぐ遊んで確認する
- 仕様、変更理由、確認結果をREADMEやメモに残す

## 9. おすすめの進め方

1. 使うゲームエンジンを1つ決める
2. 30分で作る最小ゲームを1つ決める
3. このドキュメントのプロンプトに仕様を埋める
4. AIにファイル構成と実装方針を先に出させる
5. 実装する
6. 自分で遊んで、違和感を1つだけ直す
7. 変更内容と確認結果を記録する

小さく作って遊び、直す流れを繰り返すことが、ゲーム制作におけるAI駆動開発の基本です。
